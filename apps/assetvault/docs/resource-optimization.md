# 资源占用优化（2026-10-31）

- 内置 3D 预览改为按需绘制：OrbitControls change 事件续接阻尼帧，稳定后停止。灯光拖动、尺寸变化和页面重新可见会请求重绘；材质、通道等原有主动渲染入口保留。
- 关闭预览后立即停止绘制、释放模型资源；60 秒未重开则清空内存预览缓存和 Polyfork 几何缓存，将画布缓冲缩至 1×1。保留 WebGL 上下文规避既有二次打开黑屏问题。重开取消回收定时器，尺寸变化观察器在关闭期间不重新分配缓冲。
- 普通网格的固定正方形封面使用 content-visibility:auto 跳过屏幕外内容绘制，不改变卡片 DOM、选择状态和搜索行为。瀑布流及紧凑模式排除；这不是完整虚拟列表，不会回收全部离屏图片内存。

验证：29 项直接相关测试最终全部通过（其中一项旧的持续循环源码断言适配按需渲染后单独复测通过）；生产资源构建通过。真实页面 48 张卡片封面宽高一致，FreeStylized 材质预览首帧、旋转、滚轮缩放、关闭再打开正常，未捕获控制台错误。截图：artifacts/resource-optimization/preview-reopened.png。

限制：60 秒回收及恢复尺寸用模拟定时/渲染对象验证，未实际等待回收后重开。未手动覆盖所有平台、SBSAR 参数、通道和灯光手势，相关既有路径静态测试通过。未做进程隔离的前后 CPU、内存、显存对比，不承诺降幅。平台 iframe 预览器不受内置渲染调度控制。

# 启动内存实测与收敛（2026-11-16）

面板口径先纠正：`server/resource-usage.mjs` 的 `readWindows()` 对 `Win32_Process.WorkingSetSize` 直接求和（第 65 行），WebView2 运行时共享代码页会被 6 个进程重复计入，面板自己也标了这一点。同一批 PID 实测 browser 进程工作集 139.6MB 而私有提交只有 43.9MB。因此 «841MB» 里的百兆级是重复计入，真实新增量低于该值。第九个进程按定向统计口径（browser 及其子进程 + `assetvault.exe` + `node --watch` 与后端子进程）。共享页重复计入，所以面板数字偏高；页内实时数据经 DevTools 实测。

## 页内实测数据（开发版，DevTools + 定向进程统计）

WebView2 的调试端口只监听 `::1`（IPv6 环回）；`127.0.0.1:9333` 可能被别的浏览器占用，取数时必须用 `http://[::1]:9333/json/*`，否则审到的是别的浏览器标签页。

- 全新启动：renderer 工作集 165MB / 私有提交 108MB；页面在发现页 60 张卡片时 **JS 堆仅 10MB**，DOM 8421 元素 / 22551 节点 / 2442 监听器；已解码位图约 9.9 兆像素。
- 库页滚到底（复现"用一会就涨"）：卡片 66 → 562，已解码图片 575 张、**101.8 兆像素**；renderer 工作集 165 → **331MB**、私有提交 108 → **266MB**；**JS 堆仍只有 14MB**。
- 抽掉 538 张视口外图片的 `src` 只回收 3MB：Chromium 的解码缓存不随 `src` 清空，**靠 `src` 回收无效，只能在 DOM 层不做这些卡片**。
- 空闲 CPU（页面静止、无人操作）：renderer **68.3%** + GPU **37.0%**；把 5 个 CSS 动画（4 个 `av2-eye-glow-pulse` 眼睛光晕、1 个 `av-body-breathe` 呼吸）`pause()` 后掉到 renderer **7.0%** + GPU **6.1%**，恢复正常后回到 71.9% / 36.9%。
- 面板同口径合计（9 进程工作集）：740–765MB，renderer 波动 161–172MB。

## 本轮已改（4 处）

1. `server/card-thumbnail.mjs`：卡片封面 512 → 384。依据：卡片列宽 `minmax(218px,1fr)`，`device-scale-factor=1.5` 下最小约 327 物理像素；与本地缩略图 `LIST_THUMB_SIZE=384` 统一，解码面积剩 56%。注意：本机库 736 个素材全部 `platform=local`，本来就走 `/api/local/thumb` 的 384，此改动只对"发现/图站 + 远端素材卡"路径生效。
2. `server/thumb-cache.mjs`：缓存目录改为优先 `SFX_DATA_DIR/thumb-cache`，仅在缺 `SFX_DATA_DIR` 时回落 `%TEMP%`。Windows 存储感知会清 `%TEMP%`，缓存被清后上千封面要重生成；当前 `/api/local/thumb` 生成失败会回退原始文件，一张 2048 PNG 解码十几 MB。Rust 侧本来就注入 `SFX_DATA_DIR`，因此不需要改 Rust。
3. `server/library.mjs`：`imageKey` 的 `card512-v1` → `card384-v1`；卡片图缓存头由 `max-age=604800` 改为 `private, no-cache`（ETag 复验，命中回 304）。原 7 天强缓存不改的话，浏览器不会重取改尺寸后的封面，等于白改。
4. `src-tauri/tauri.conf.json` 窗口对象新增 `additionalBrowserArgs`：`--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection --enable-low-end-device-mode --disk-cache-size=268435456`。自定义该字段后 wry 默认的 `msWebOOUI/msPdfOOUI/msSmartScreenProtection` 需要自己重带，否则内嵌面板行为回归。

验证：三个 .mjs `node --check` 通过，`tauri.conf.json` 解析通过；`cargo check --no-default-features` 通过（仅原有两条 `data_path.rs` dead_code 警告）；`cardThumbnail()` 对 900×600 PNG 输出 384×256 webp；`thumbFor()` 在 `SFX_DATA_DIR` 下把缓存写进 `data/thumb-cache`；重启后 browser 进程命令行确认新参数生效；重启后 renderer 165MB / commit 108MB（此前旧实例曾累积到 1757MB / 1691MB）。

## 未做与限制

- 未做 DOM 级窗口化（真虚拟列表）。数据已证明 `src` 回收无效：必须在卡片滚出视口后销毁节点、滚回时重建。这是把 331MB 压回 165MB 的唯一可行路径。
- 未处理那 5 个常驻 CSS 动画。它们是空闲时约 60 个百分点 renderer CPU + 31 个百分点 GPU 的来源；可行方向是仅在窗口可见/聚焦时播放（`visibilitychange` 控制 `animation-play-state`），或把动效从 blur/box-shadow 改为纯 transform/opacity。
- 未改 `main.rs:331` 的 `#[cfg(debug_assertions)] cmd.arg("--watch")`：只影响开发版（多一个 ~37MB 的 watcher），发布版本来就没有，改了对最终用户无收益且会破坏 dev 热重启。
- 1.75GB 那个旧实例未复现：全新启动并空闲 4 分钟只稳定在 161–172MB，说明旧数字是长时间浏览/多次页面重载的累积态，不是启动基线。

## 资源面板统计口径调整（2026-11-16）

主指标改为 Windows 原生计数器的私有驻留内存；工作集汇总、私有提交在总览和模块表中分别列出。缺失或无法读取的计数显示“不可用”，不回退冒充另一种指标。私有驻留不含共享页与独立显存，不能视为应用全部物理占用。

系统内存分布只显示系统已用与可用，不再用含重复共享页的应用工作集拆分“其它”。诊断 JSON 新增 privateWorkingSet、privateCommit、workingSet 与 used，保留原 app / group.memory 工作集字段以兼容旧诊断消费者。
