# AI 找资产：自然语言 → 画板

> 状态：2026-11-18 已实现 P0、可选 P1 及 P2 的多关键词、已有库／混合查找、每日收集、单图精查；已完成隔离浏览器中的真实搜索、入板、视觉评分、移出引用与刷新恢复。计划解析实测超时，已验证降级；尚不能认定所有平台与原生桌面均验收通过。
> 下文保留接口设计与验收要求；实现范围和限制见第 9 节，不能把待验收项目视为已实测通过。
> 相关文档：[画板体系](board-development.md)、[资产库](asset-library-development.md)。

## 1. 目标与操作边界

用户输入需求，确认条件后，查找平台资产、保存记录并添加到画板；可选用缩略图拼图进行视觉复核。

**添加到画板不等于下载原文件。**

| 操作 | 本功能是否执行 |
| --- | --- |
| 保存名称、来源链接、缩略图地址、类型、标签等元数据 | 是，资产库保留记录 |
| 把资产 UID 引用加入目标画板 | 是，不复制第二份资产 |
| 获取缩略图供预览、拼图，产生临时或代理缓存 | 是，按既有预览机制 |
| 下载模型、材质贴图包、原始图片、视频等原文件 | 否；用户另行点击“下载” |
| 将远程资产变成可离线使用的本地文件 | 否；原文件未下载时不能承诺离线可用 |
| 取消画板引用时删除资产记录或本地文件 | 否 |

确认条固定显示：**“仅保存记录并添加到画板，不下载原文件”**。结果计数区分“找到 / 已入库 / 已入板 / 已复核”，不得用“已下载”描述采集成功。

## 2. 分期与最小路径

### P0：一次搜索并添加到画板

最短路径：输入需求 → 点击“AI 找资产” → 条件可直接编辑 → 点击“添加到画板” → 完成后“打开画板”。

- 默认新建普通画板，也可直接选择已有普通画板；智能规则画板不作为手动写入目标。
- 默认一次执行，规则 `frequency:'manual'`。保存规则不代表自动订阅。
- 每次只执行一个主关键词查询；`keywords[]` 先作为可点击替换词，不自动并发搜索。
- 不做文本重打分，不做视觉筛选，不自动下载。
- 继续使用现有平台搜索、预算守卫、待合并队列、画板引用与持久化。

### P1：可选视觉复核

- “视觉复核”默认关闭；新增拼图与视觉评分端点。
- 入库、入板完成后，只复核本次成功添加的候选；不自动处理画板中原有资产。
- 显示推荐结果与待定项，用户可一次点击“移出未通过项”；不默认移除。
- “移出”只删除画板引用，资产记录和原文件均保留。

### P2：本轮授权后的扩展

- 多关键词召回：设定总候选与平台调用预算，合并去重后统一截断。
- 已有资产库查找、混合来源、单图精查；“资产库”包含已保存的远程记录，不等于只查磁盘文件，不扫描或重新导入文件。
- 用户主动开启每日收集；不默认订阅，不自动调用视觉 AI。后台复核、关闭前端后的持续视觉处理仍需单独设计，不属于本轮明确功能。
- 不承诺用缩略图判断分辨率、无缝平铺、许可证或文件是否可下载。

## 3. 现有能力与必须调整的部分

| 能力 | 当前事实 | 本功能处理 |
| --- | --- | --- |
| 平台注册表 | `server/collect-search.mjs` 的 `COLLECT_PLATFORMS` 含可搜索能力 | 校验白名单，并遵循当前平台启用、登录与预算状态 |
| 收集规则 | 保留单 `query` 兼容旧规则，新增 `queries / scope / maxCalls` | 主关键词与最多两个扩展词，类型复用 `filters.kinds` |
| 执行 | `POST /api/collect/run` 等待 runner 完成后才返回 | 保留同步请求，不新建任务调度框架 |
| 历史记录 | `/api/collect/runs` 保留 requestId、状态和本轮候选 | 支持精确恢复，不伪造实时数量进度 |
| 入库 | runner 将模型元数据写入 `collect-pending` | 必须合并并等待服务端持久化完成，才可 ack |
| 入板 | runner 按 UID 添加引用，可能独立失败 | 校验 `board.ok`，失败只重试入板，不重搜 |
| 候选 | requestId 结果持久化 candidates 与 addedUids；dryRun 仍仅返回前 24 条预览 | 不从全局 pending 猜本轮结果 |
| 去重 | 旧规则默认全局 seen；AI 找资产显式 dedupe:board | 已有资产可复用到另一画板，目标画板原有成员跳过 |
| 打开画板 | `boardHub.openBoard(id)` 处理路由与查询作用域 | 复用完整入口，不只调用 `store.setActive()` |

**开发范围不是“只加两个 AI 端点”。** P0 还需收集运行契约、入库同步确认与失败恢复的小范围调整；这些是验收前置条件。

## 4. P0 完整流程

1. 校验需求，调用 `POST /api/ai/hunt-plan`。
2. 展示确认条：目标画板、关键词、类型、平台、数量都可直接编辑，无需重新询问 AI。
3. 用户确认后生成稳定 `requestId`，禁用重复提交。
4. 已有画板直接使用；新画板创建一次，记录其 ID。
5. 保存 manual 收集规则，关联 `boardId`；规则与本次请求 ID 要建立可恢复关联。
6. 调用 `POST /api/collect/run`，显示“正在查找”，不伪造百分比或 `N/M` 实时计数。
7. 获取本轮结果，复用 `syncPending()` 的合并逻辑：
   `pending → mergeModels → persistNow → 等待保存成功 → ack`。
8. 校验本轮记录已持久化、画板写入成功；刷新画板与资产库当前查询。
9. 显示实际结果。点击“打开画板”调用 `boardHub.openBoard(boardId)`。

本轮已补足 `syncPending()` 的保存确认，调用 `persistNow()` 后等待 `storage.flush({strict:true})` 成功才 ack。不能退回“队列空闲即成功”，也不能用 toast 代替错误返回。

保存确认分两层：`persistNow()` 同步校验 / 序列化 / 本地写入失败应返回明确失败；使用 `persistent-storage` 时，还必须等待此次数据的服务端写入结果。仅返回 boolean 不能证明异步服务端保存成功。复用既有存储队列，补充可返回成功或失败的确认接口，不另建持久化系统；失败不 ack。同步更新 `board-collect.js` 关于“不会因 ack 提前丢数据”的注释，避免把目标保证写成当前已实现能力。

### 4.1 运行契约

现有请求 `{id,dryRun}` 保持兼容。AI 找资产额外传入 `requestId`，由服务端用于单次运行的幂等与恢复；绑定 ruleId 与规范化输入摘要。

- 保留 `collect-api.mjs` 的请求并发闸门，避免重复创建运行记录；P2 在 runner 加入所有调用方共用的执行闸门，覆盖原先绕过 API 的每日调度。旧客户端并发请求仍可返回 409；调度遇到同规则正在执行则跳过。
- 规则锁只防同时运行，不能防请求结束后的重复执行，也不能跨进程重启保证幂等；requestId 的已完成结果查重仍然必要。
- 原有全局 seen 只减少重复资产，不防重复平台搜索，也不保证添加到另一画板；不得以 seen 替代运行幂等。

- 相同请求 ID 与相同输入：运行中沿用规则锁返回 409，前端点击“核对结果”按 requestId 查询状态；已完成返回同一结果，不重复搜索。新的 requestId 表示新一轮，可能再次产生平台请求与 AI 费用。
- 相同请求 ID 与不同输入：明确拒绝，不能复用旧结果。
- 在搜索前记录 `running`；结束就地更新同一条记录为 `completed / partial / failed`。同一次运行只占一个历史名额，不得开始、结束各追加一条，避免消耗现有 runs 上限（200 条）；被中断的记录同样更新原条目。
- 完成结果包含 `candidates[]`（本轮候选摘要）、`addedUids[]`（本轮新加入目标画板的 UID）、`board`、平台错误与实际数量。
- `candidates` 最多 60 条，包含 UID、名称、来源、缩略图地址、类型；不包含原文件数据。
- 恢复查询按 `requestId` 精确定位；不得读取“最新一条 run”猜测当前任务。
- `normalizeRun`、持久化与 API 返回均需保留新增字段；只修改 runner 返回对象不够。
- 不引入新的调度系统；应用重启后未完成记录标记为中断或待核对，不自动重跑。
- requestId 不自动保证前端建板 / 存规则的幂等。前端为新画板、规则生成确定性 ID，按现有 upsert 语义保存；响应丢失时仍复用同一 ID，不创建第二份。

### 4.2 去重与目标画板

- 资产身份继续使用既有稳定 UID，同一资产不重复入库。
- AI 找资产使用显式策略，区分“已见过”与“已在目标画板”：前者可复用，后者跳过。
- 默认旧采集规则仍维持原全局去重语义；新增策略必须由 AI 找资产显式选择并保存。
- 类型和平台搜索失败不能伪装成成功；返回跳过原因。
- 只入板失败时，用本轮候选 UID 重试 `boardItems`，不能再次采集。

## 5. AI 计划端点

`POST /api/ai/hunt-plan`

请求：

```json
{"prompt":"收集风格化的木板材质","scope":"platform","limit":24}
```

接受 `scope:'platform' / 'local' / 'both'`，默认 platform；非法来源明确拒绝。local 的采集过程不联网搜索平台，计划解析与用户手动视觉复核仍可能调用已配置 AI。

响应示例：

```json
{
  "boardName":"风格化木板材质",
  "kind":"textures",
  "rule":{
    "query":"stylized wood planks",
    "platforms":["freestylized","ambientcg"],
    "scope":"platform",
    "filters":{"kinds":["textures"]},
    "limit":24,
    "frequency":"manual"
  },
  "keywords":["hand painted wood texture","cartoon wood material"],
  "explain":"查找可用的风格化木板材质",
  "degraded":false
}
```

- 一次文本调用产出全部字段，复用现有 AI 配置、JSON 解析和并发守卫。
- `prompt` 1–300 字；超限服务端拒绝，前端提示修改，不偷偷改变原意。
- `limit` 有限整数，夹到 1–60；平台去重，最多 12 个，只允许注册表中支持搜索且当前可用的平台。
- `limit` 是本次所有平台合并、去重后的候选数量上限，不是每平台上限，也不是保证收集到的数量。现有执行器按 `per = max(3, ceil(limit / 平台数) + 2)` 分配单站请求数量，再截取总结果到 limit；例如 3 个平台、limit=24 时，各站请求最多取 10 条，最后总数最多 24 条，实际还受单页结果、过滤、去重与平台失败影响。P0 不自动补足短缺。
- `kind` 使用现有类型注册表真值；落到 `filters.kinds`，不得只在 UI 展示。未知值留空并提示。
- 归一化类型过滤复用 `filterItems / normalizeFilters / matchesFilters`，不另写过滤层。真实搜索发现 FreeStylized 默认模型会使材质查询被全部筛空，因此补充类型下推：只有一个明确 kind 时，FreeStylized、Poly Haven、ambientCG 通过已有原生 type 搜索对应类别；返回后仍统一校验 filters.kinds，不把原生筛选当成最终保证。
- `query` 去控制字符、限制长度；不要把删掉引号和括号当成安全机制。输入作为数据处理，结果用文本节点或转义渲染。
- 板名遵循现有画板校验，不把虚拟画板当物理文件夹；只有导出路径才执行文件名安全规则。
- 默认平台按类型与平台能力选择；风格化材质优先 FreeStylized。参考图不能冒充材质，模型包不能冒充独立贴图。
- `keywords[]` 仅是可直接点击替换的备选词，P0 不自动执行。
- P2 只有用户把扩展词填入确认条时才执行多关键词；AI 返回备选词不会自动增加平台请求。
- 未配置 AI、鉴权失败、超时、非 JSON：返回 `degraded:true` 和明确原因，保留原始关键词。平台检索是否有结果另行报告。
- 未识别类型时让用户直接选择或保持“全部”，不保证中文关键词直搜一定召回。
- 缓存至少包含需求、数量、作用域、可用平台集合及 AI 配置版本；不跨配置复用旧计划。

## 6. P1 视觉复核契约

`POST /api/ai/rank-sheet`，复用现有 vision 通道，不新增模型配置入口。

前置依赖：P0 的运行结果与持久化记录必须包含本轮 `addedUids`；字段缺失时不得启用“移出未通过项”，也不能用当前画板全部成员代替。

```json
{
  "goal":"手绘风格木板材质，不要写实扫描",
  "sheet":"data:image/jpeg;base64,...",
  "count":16,
  "cols":4,
  "rows":4
}
```

```json
{
  "status":"ok",
  "scores":[
    {"index":3,"score":92,"why":"手绘色块明显"},
    {"index":7,"score":42,"why":"风格不确定"},
    {"index":9,"score":12,"why":"更接近写实扫描"}
  ],
  "note":""
}
```

- 服务端只返回序号与评分，不转换 UID。前端用不可变 `batch[index-1].uid` 映射。
- `index` 为 1..count 整数，`score` 为 0..100 有限数；非法条目丢弃，重复编号保留最高分。
- 仅保留一个 `scores` 数组，避免 picks / rejected 同一编号冲突。
- `status` 仅描述整次视觉调用（ok / unsupported / failed）。在合法响应中，去重并过滤非法评分后 `scores.length < count` 表示部分项未评估；不为此再新增 partial 状态。合法但无评分不能伪装为有效低分。
- ≥70 推荐；40–69 待定；<40 未通过；未返回编号、缩略图失败或不可判定均为“未评估”，保留引用。
- 单张拼图的分数是绝对匹配参考，不承诺不同拼图之间精确可比；P1 不强制改画板排序。
- `status:'unsupported' / 'failed'` 与有效低分必须区分。调用失败保留所有候选，不能视为全部未通过。
- 删除建议只允许操作该 requestId 的 `addedUids` 交集，避免改动画板原有引用。
- 用户确认“移出未通过项”后仅调用 `boardItems(...,'remove')`。可见待定项让用户直接选择，不能藏到多层菜单。
- 更改关键词、平台或候选集会使旧评分失效；用 requestId 与批次标识丢弃晚到结果。

### 6.1 拼图与资源管理

- 每批最多 16 项，固定 4×4、单格 512px、总图 2048²，JPEG q0.82。
- 图片等比完整放入单格并留编号区域，禁止拉伸；空格不编号。
- 每张图独立超时与失败占位，保持原始索引，不能删除失败项后把编号前移。
- 缩略图使用既有同源代理；检查 HTTP 状态、图片解码与尺寸，不能下载原文件替代封面。
- 限制并发取图（建议 4）；每次绘制后 `ImageBitmap.close()`；创建的对象 URL 及时释放。
- 拼图上限沿用路由请求体限制，明确计算 JSON 与 base64 开销；超限降低质量或拆批。
- 前端与服务端分别执行下表中的检查，不为拼图验证新增 sharp / canvas 依赖。前端检查是生成正确拼图的保证，不能替代服务端输入边界校验；服务端不宣称已验证实际图片像素或视觉格子内容。
- 模型请求的 detail / 图片缩放可能降低有效单格分辨率，不宣称每格实际被模型按 512px 识别。
- 20 条候选首次复核为 2 次视觉请求；默认不自动重试，手动重试须说明额外调用。3×3 重拼属于不同批次，必须重新映射。
- 缓存包含图片哈希、goal、count、cols、rows、模型配置版本；不缓存临时失败。

| 校验位置 | 必须执行 |
| --- | --- |
| 前端 | 取图 HTTP 状态、解码成功、`bitmap.width/height > 0`；输出画布为 2048×2048；固定 4×4、count 为 1–16；batch 顺序与编号一致；失败项占位且不前移；base64 输出体积受限 |
| 服务端 | 请求体字节上限；仅允许约定的 data URL MIME 与规范 base64 数据；拒绝 URL 直传；goal 为 1–300 字；批量 count 为 1–16 的整数，cols=4、rows=4；单图精查仅允许 count=1、cols=1、rows=1；不可信输入校验后才发给模型 |

### 6.2 单图精查

- 复核结果每一项直接显示“单图精查”，一次点击执行，仅用于本轮 addedUids 内候选。
- 使用已有封面，等比放入 1536×1536 画布、JPEG q0.85，编号固定为 1；不为提高分辨率下载原文件。
- 沿用 rank-sheet，参数 count=1、cols=1、rows=1；缓存键包含布局，因此不与 4×4 拼图串用。
- 按键提示会增加一次视觉请求；用户主动点击才执行。成功只更新该项评分，失败保留已有评分与画板引用。
- 封面小、缺失、模型能力不足时不保证精度；“精查”指给单项更多有效画面，不承诺获取高清原图。

## 7. 交互与恢复

- 同一搜索框在发现页和资产库均可显示入口，仅非访客可用；在输入框邻近挂确认条，不挂到可能隐藏的 `#discovery-controls`。
- 输入框已有 `#theme-breakdown-btn`（AI 拆解），保留原按钮及一次点击拆词的链路。P0 在搜索框相邻操作区增加短文字按钮“找资产”，点击一次直接生成计划；不得再放一颗相同 sparkle 图标，不用二档菜单，也不能要求先生成计划才能拆词。两个入口使用不同名称与 aria-label，各只触发自己的 AI 请求。
- 仅在用户点击 AI 入口时解析，不把每次普通输入变成 AI 请求。
- 确认条默认一行摘要与直接可改的条件；低频说明用 tooltip，不展开三行常驻说明。
- 不额外设“改条件”入口才能改常用参数；点击当前关键词、平台、数量或目标画板即可编辑。
- 确认条明确“不下载原文件”；视觉复核开关只在 P1 可用后显示。
- 前端状态：`idle → planning → planned → running → syncing → ranking(可选) → done/done-warnings`。done-warnings 表示流程完成但存在告警；后端 run 的 partial 专指部分平台或写入失败，前端将其映射成告警，不混用两个状态的含义。
- 提交前可取消计划；关闭面板不等于取消后台采集。仅在真正支持服务端取消后才显示“取消采集”。
- 运行中不阻塞资产库其他操作，切路由回来可恢复本次状态。
- sessionStorage 保存 requestId、boardId、ruleId、阶段及恢复必需的计划与原始需求；不保存拼图 base64。存储失败会提示保持窗口打开，此时不保证刷新恢复；关闭整个窗口后不保证会话状态保留。

| 失败位置 | 行为 |
| --- | --- |
| 计划失败 | 保留需求，给出降级计划或明确错误 |
| 建板成功、规则保存明确失败，尚未启动 | 可清理本次新建且仍为空、无规则关联的画板；已有画板绝不删除 |
| 运行请求超时、断网、响应丢失 | 标记状态未知，按 requestId 核对；不删板、不重建规则、不自动重新采集 |
| 部分平台失败 | 保留成功结果，显示失败平台，允许有预算地重试 |
| 入库保存失败 | 不 ack，保留 pending 并允许重试合并 |
| 入板失败 | 保留记录，只重试本轮 UID 入板 |
| 视觉失败 / 前端关闭 | 已入库入板结果保留，显示未复核；可恢复后手动继续 |
| 无结果 | 保留输入和可编辑计划；不保证外站一定达到目标数量 |

## 8. 验证与验收

### P0 自动验证

- 假 AI 验证输出校验、类型落入 filters、非法平台、未实现作用域、降级与配置缓存失效。
- 假平台结果包含模型与材质，确认材质规则不会混入模型。
- 相同 requestId 重试只执行一次；超时后可找回同轮结果，重启中断不自动重复调用。
- 同资产重复添加同画板不重复；添加另一画板可复用，不受旧全局 seen 阻断。
- 入库保存失败不能 ack；恢复后可重试；确认资产库与画板均无需手动刷新。
- run 的候选清单经过序列化、历史存储后仍可恢复，不从全局 pending 混入其他任务。
- 原文件下载入口未被调用；未创建模型或贴图下载任务。
- 入板失败不重搜；已有画板和原有成员不受失败清理影响。

### P1 自动验证与人工抽检

- 16 / 20 / 60 项按 16 分批，编号与 UID 固定映射；失败封面不使后续编号错位。
- 非方形图片不拉伸，尺寸调整不裁掉编号，位图与 URL 释放。
- 无评分、有效全低分、unsupported、超时分别处理；未评估项保留。
- 评分晚到不覆盖新计划；只能移出本次 addedUids，不能删除原有成员。
- 假模型测试只验证协议与流程，不冒充视觉精度验证。
- 真正视觉质量需用户授权使用模型后，以固定样本集逐项记录人工判断、误拒率、请求数和耗时。

### 验收口径

- 固定假平台样本：一次操作完成保存记录与入板，零原文件下载任务，无需手动刷新。
- 真实平台：记录实际返回数量、错误与耗时；“30 秒至少 8 项”不作为强制指标。
- P0 不宣称多关键词召回、每日订阅或视觉筛选已经完成。
- P1 默认 20 项首次复核最多 2 次视觉请求；视觉失败不丢资产。
- P2：3 个关键词×多个平台最多执行 maxCalls 次，最终总候选不超过 limit；local 不调用平台，已有记录不重写；混合来源按 UID 去重；daily 默认关闭且可直接停止；单图仅对选中项增加一次视觉请求。
- 实测操作路径保持输入 → AI 入口 → 确认 → 打开画板，不增加“更多 / 管理 / 更换”等中间入口。

## 9. 本轮实现与待验证边界

- 入口是搜索框旁的“找资产”，保留原有拆词图标；条件直接编辑，点击“添加到画板”执行，完成后可直接“打开画板”，没有二级菜单。
- P0 已接入计划解析、类型过滤、按目标画板去重、运行记录就地更新、精确恢复与入板失败重试。旧规则默认的全局去重不变。
- 保存链路使用 persistNow 的布尔结果与 storage.flush({strict:true})；保存失败不 ack，重试成功后才确认待合并队列。
- P1 已接入固定 4×4 拼图、分批评分与手动移出引用；复核保留原始需求，未评估项不自动移除。恢复任务后需要手动点击“视觉复核”，不自动产生新的视觉请求。
- 入板失败可直接重试本轮候选，不重复搜索。重试新增成员未写回权威 addedUids 快照，因此不提供本轮自动移出建议，以免误动原有成员。
- 后端重启遗留的 running 记录显示 interrupted。用户核对画板后可开启新需求，不自动重新调用平台。
- 模拟测试覆盖计划边界、响应丢失、重复请求、保存失败不 ack、跨画板复用、入口到入板、拼图编号比例、多关键词预算、混合来源、每日配置保留及单图精查。相关测试通过，前端构建通过并同步桌面版 26 个资源文件。
- 真实只读搜索抽检：FreeStylized 的 wood+textures 返回 3 条材质，约 5.1 秒；ambientCG 的 wood 返回 3 条材质，约 6.9 秒。仅检查搜索模块，不写用户库、不下载原文件，不代表所有平台已验收。
- 隔离实测使用 `node scripts/test-ai-hunt-live.mjs`：复用当前 AI 配置，独立临时数据、资产、下载和账号目录，不写正式资产库；正常信号退出包含凭据清理。仅监听 127.0.0.1，不启动每日调度。本次 Windows 终端中断未确认执行清理，随后删除临时配置的命令被执行策略拒绝，不能声称凭据副本已清除。
- 可见浏览器实测：FreeStylized 的 wood／材质找到 5 项，总上限 3，实际入库、入板各 3；待合并队列确认保存后归零。仅请求平台封面，没有下载原始资产包。

- 实测修复：从“找资产”打开画板会先清除需求搜索词，防止画板有成员却被搜索词筛空；入口仍为一次点击。相关 27 项测试通过，修复后受影响的 8 项流程测试通过，前端构建通过。
- 原生桌面布局、所有平台与单图精查的真实 AI 调用未逐项验收；每日调度以自动化测试验证，未等待真实跨日。验收截图：`docs/ai-hunt-live-proof.png`。

- 无结果缩词：平台搜索经过类型过滤仍为零时，在已有扩展词之后按预算尝试最多两个英文核心词，仍最多三个查询与 maxCalls 次搜索；不改原需求、不放宽类型、不自动保证风格匹配，纯本地查找不触发。截图条件 `stylized stone brick wall texture`＋ArtStation／ambientCG／Poly Pizza／FreeStylized 实测原词零项，缩到 `stone brick` 后 16 项材质，共 8 次搜索。此项使用真实搜索、隔离规则与替身画板，不写正式库。

- requestId 生命周期、运行记录保留时长与候选元数据容量沿用现有存储上限制定；清理记录不得删除资产与画板。
- 平台禁用、登录失效与配额耗尽时的默认回退组合，以实时能力为准。
- 视觉是风格与题材辅助判断，不能证明文件内容、版权、可商用或下载可用性。

## 10. P2 执行与预算契约

- 确认条新增来源、扩展词、调用上限、每日收集及时间，均直接编辑。主关键词最多 300 字，扩展词最多两项，用分号分隔，默认留空；去重后最多执行三个词。
- scope=local 不要求平台；scope=both 先查已有资产，再查选定平台。已有资产查询复用资产库类型、标签、回收站与搜索语义，排除回收站；不引入文件导入或下载。
- maxCalls 为每轮平台搜索调用总预算，整数 1–12，默认 12，按统一 search(platform,...) 的调用计数，不等于适配器内部原始 HTTP 请求数。各平台先执行主关键词，再按扩展词轮转；每次调用前仍检查平台启用、冷却和小时配额。达到预算后明确提示，不自动补调用。预算不包含 AI 计划与视觉请求。
- 单站请求数量按实际预计调用数分摊：per=max(3, ceil(limit/min(maxCalls,平台数×词数))+2)。总结果按稳定 UID 去重、排除目标画板已有成员，再统一截取至 limit（1–60），不保证补足数量。混合来源优先已有库记录，避免重写已有标签、路径与元数据。
- 每日收集默认关闭，必须用户手动勾选；沿用本地时间 0–23 点与既有 60 秒调度心跳。仅后端运行时执行，关闭后端不后台唤醒系统，也不承诺精确到秒。
- 每日执行保存记录、添加画板引用；待合并记录由前端轮询持久化后 ack。关闭前端时 pending 保留，重新打开后合并；每日不自动调用视觉 AI，不下载原文件。
- 完成面板直接显示“停止每日收集”；全部规则也可在现有智能收集面板暂停、编辑或删除。停止不删除已收集资产与画板。连续点击“再找一轮”复用同目标规则，生成新的 requestId，不制造多条重复订阅。
- 手动与定时执行共用 runner 的规则锁；调度遇到忙碌直接跳过。失败写运行记录并推进下次每日时间，避免一分钟一次不断重试平台。
- requestId 的输入指纹包含 scope、queries、maxCalls；更改条件不能复用旧结果。后台每日完成记录保留本轮候选与 addedUids，但不冒充前端实时进度。
