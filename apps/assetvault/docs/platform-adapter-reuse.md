## 公共件实际契约

```js
listPager({
  initialState,
  maxPages,
  fetchPage,
  consume,
  nextState,
  isLimitReached,
  partialOnError = false,
})
```

- `fetchPage(state)`：调用站点现有请求函数，返回响应；鉴权、超时、重试、Referer、响应校验留在原请求链路。
- `consume(response, state)`：同步执行站点原有过滤、去重、映射和追加。当前页状态用于花瓣首屏元数据判断；不依赖返回值，不吞掉映射错误。
- `nextState(response, state)`：由适配器判断来源是否结束；返回 `null` 停止。公共层不猜响应结构，不强制重复游标保护，也不因无新增 item 自动停止。
- `isLimitReached()`：本页消费后判断是否停止。首次请求前是否检查、页内是否截断，仍由适配器保留原来的 for/do-while 语义。
- `maxPages`：显式传原限制，Flickr 使用 Infinity；不统一增加 10 页上限。
- `partialOnError`：首页请求失败始终抛错；后续页仅在本站原来允许时返回部分结果。500px、花瓣保持直接抛错；Pexels、Civitai、Wallhaven、Flickr 保留已有部分结果。

内部返回 `{reason, pages}`，其中 pages 为成功请求页数；部分失败额外返回原 error：

| reason | 含义 |
| --- | --- |
| source-end | 适配器的原有终止条件命中 |
| item-limit | 本次数量限制命中 |
| page-limit | 原有请求页数上限命中 |
| partial-error | 按本站策略保留部分结果，附原异常 |

上述信息只用于内部诊断和单测，没有接入外部 `truncated`、完成状态或总数计算。`source-end` 沿用原适配器判断，不额外保证真实网站已无更多资源。

## 开发中纠正的假设

1. Civitai 不支持关键词检索；原图片列表不去重、按整页追加，零上限仍抓一页，重复游标一直受原页数上限约束。
2. Wallhaven 同样按整页追加，但首次请求前检查限制、按图片 URL 去重，不能套用 Pexels 的页内截断。
3. Flickr 原来没有固定页数上限，且相册作者查不到仍可按相册 id 获取图片。
4. 500px 与花瓣后续页异常原本会抛出，不能统一改成部分成功。
5. 花瓣不是统一的 HTML 分页：主页用户名解析使用 HTML，画板/图片/搜索使用 API，搜索靠 page、画板靠 max、画板列表靠 seq。
6. 花瓣图片循环零上限仍会追加首个有效 item；保留这一行为，未混入参数修复。
7. 两站试迁时发现的后续页 AbortError 被部分成功策略吞掉，已用基线测试记录；本轮没有改变该既有取消语义。
8. 原 video-sites 测试只认四个素材视频站，但注册表已有额外四个短视频站。本轮已修正为同时覆盖两类；素材视频检查首页，短视频检查分享入口，不改产品注册表。
